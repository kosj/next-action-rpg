# 대표 아트 구간 · 제작 및 검수 계약

작성일: 2026-10-30. 첫 범위는 **리라 몸체·룬검, 근접 수호병·검, 순례자 전투 공간의 모듈 키트**입니다. 제작 입력은 [asset_specs.json](../art_source/production/asset_specs.json), 모션 계약은 [motion_contract.json](../art_source/production/motion_contract.json)에 있습니다. 현재 2D 콘셉트가 존재하며 3D 모델·스킨·클립·실제 게임의 최종 품질은 아직 검수 전입니다.

## 사용 가능한 참조와 남은 제작

| 대상 | 현재 입력 | 실제 제작에서 확인할 항목 |
|---|---|---|
| 리라 | [무기 없는 단일 전신 콘셉트](../art_source/production/references/lyra-front-concept.png) | 얼굴·손·묶은 은회색 머리·흑철/청록/금색 분리, 어깨/무릎 가동과 의상 간섭 |
| 근접 수호병 | [무기 없는 단일 전신 콘셉트](../art_source/production/references/sentinel-front-concept.png) | 큰 후광 장식의 분리/축소, 긴 천의 분할/단축, 손가락·어깨·머리 회전과 공격 예고 가독성 |
| 전투 공간 | [구도와 재질 목표](../art_source/production/references/sanctuary-courtyard-target.png) | 개별 기둥·문·바닥·화로로 조립, 중앙 전투 공간과 출입구 가독성, 플레이 카메라에서 재질/조명 일치 |

세 이미지는 네이티브 이미지 생성 도구로 만든 개발용 2D 콘셉트입니다. VARCO 생성 모델·최종 리그·실제 게임 화면으로 표시하지 않습니다. 출처와 SHA-256은 [참조 manifest](../art_source/production/references/manifest.json)에 보관합니다.

## G0 · 생성 입력 확인

- `asset_specs.json`의 `single_view`는 캐릭터 생성용 한 장의 전신 이미지입니다. 다면도 프롬프트는 의상과 비례 일관성 검수용이며 여러 인물의 시트를 그대로 image-to-3D에 넣지 않습니다.
- 무기와 몸체를 분리합니다. 손에 붙은 무기나 몸체에 합쳐진 칼집은 본체 스킨 후보에서 제거합니다.
- 환경 목표 그림은 전체 장면을 한 메시로 생성하는 입력이 아닙니다. `module_targets`에 따라 한 모듈씩 단독 후보를 만듭니다.
- 공식 MCP의 실제 도구 스키마·대상 Flow·생성 모델·지원 입력을 확인하고 입력 명세를 번역합니다. 이 JSON을 미확인 도구의 API payload로 그대로 보내지 않습니다.
- 생성 전 자산별 공개 범위·라이선스·귀속 조건을 확인합니다. 생성 후 영구 출처·모델 버전·가능하면 seed·입력 해시·수정 이력을 기록합니다.

## G1 · 후보와 Blender 후처리

후보는 기존 게임 GLB를 덮어쓰지 않고 별도 폴더에서 검수합니다. 최소한 다음을 확인합니다.

- 리라는 발바닥 기준 y=0, 목표 신장 1.82m입니다. 수호병은 현행 일반 적 캡슐에 맞춰 1.95m를 목표로 합니다. 실제 신장과 실루엣을 캡슐·문·카메라와 비교합니다.
- 게임 전방은 -Z, 표준 반입 자산 전방은 +Z입니다. 현재 ActorVisual의 180도 래퍼 보정과 메시 내부 회전을 중복 적용하지 않습니다.
- 얼굴·손·팔꿈치·어깨·무릎의 루프와 스킨 웨이트를 수작업으로 확인합니다. 원형 장식·천·머리카락을 몸체와 무리하게 붙인 생성 결과를 그대로 통과시키지 않습니다.
- 수호병 참조의 큰 rigid halo는 독립 부착물로 만들거나 축소합니다. 어깨를 올리고 고개를 돌렸을 때 충돌하면 제거합니다. 긴 tabard는 무릎·발에 닿지 않는 분할 패널로 단축하며, 참조의 짙은 와인색은 잿빛 천과의 대비를 검수한 뒤 선택합니다.
- 본체/무기는 별도 원본입니다. 검은 그립 중심을 원점으로, 칼끝 +Y·가드 +X·넓은 날 면 법선 +Z를 기준으로 반입합니다. 오른손 BoneAttachment3D에서 포즈마다 그립을 확인합니다.
- glTF의 base color는 sRGB, normal과 ORM은 linear입니다. normal은 OpenGL +Y, ORM은 R=AO/G=roughness/B=metallic로 슬롯을 확인합니다. 방향광·접촉 그림자를 albedo에 굽지 않습니다.

모델 구조 검사와 Blender 프로세스 정상 종료·재질·변형·실제 화면 검수는 각각 별개입니다. 자동 GLB 보고서가 정상이어도 시각 품질을 합격 처리하지 않습니다.

## G2 · 스켈레톤과 9개 모션

동일한 rest skeleton과 BoneMap을 사용하고, AnimationPlayer는 클립을 보유하며 AnimationTree가 표현을 제어합니다. 실제 이동·공격 판정·무적·보상은 게임 코드가 소유합니다. 모든 클립은 in-place로 내보냅니다.

| 클립 | 첫 길이 / 루프 | 현행 코드와 맞춰야 할 조건 |
|---|---|---|
| idle | 1.80초 / 루프, 제작 목표 | 두 발·루트가 이동하지 않으며 루프 이음새가 보이지 않음 |
| walk | 0.48초 / 루프, 제작 목표 | 기본 이동 6.4m/s에 맞는 빠른 전투 조깅. 보행 이름만 같은 느린 모션을 강제 배속하지 않음 |
| run | 0.40초 / 루프, 제작 목표 | 8.5m/s sprint와 실제 측정 속도를 사용해 발 접지를 비교 |
| dodge | 0.32초 / 단발, 코드 | 코드 이동 17m/s·무적 0.29초·쿨다운 0.48초. 방향별 연출 범위를 별도 확인 |
| light_1 | 0.52초 / 단발, 코드 | 준비 0.13 / 판정 0.17 / 회복 0.22초, 판정 구간 [0.13, 0.30) |
| light_2 | 0.52초 / 단발, 코드 | 같은 시간, arc 150도·lunge 4.5m/s. 역방향 칼질로 임의 교체하지 않음 |
| light_3 | 0.70초 / 단발, 코드 | 준비 0.18 / 판정 0.22 / 회복 0.30초, 판정 구간 [0.18, 0.40) |
| parry | 0.22초 / 단발, 코드 | 성공하면 코드가 즉시 창을 닫음. 성공 반응이나 쿨다운 0.65초가 패링 창을 늘리지 않음 |
| hit | 0.15초 / 단발, 코드 | 경직 0.15초와 무적 0.70초를 구분. 무적이 끝날 때까지 캐릭터를 고정하지 않음 |

초 단위 타임스탬프가 원본입니다. 60fps를 제작 기준으로 쓰더라도 .13초 같은 값을 정수 프레임에 반올림해 판정 경계를 바꾸지 않습니다.

현재 세 약공격은 모두 `CombatStrike`에서 `-arc/2 → +arc/2`의 같은 부호로 수평 방향을 검사합니다. 2타를 반대로 베거나 3타를 수직으로만 내리치는 모션을 만들면 기존 판정과 어긋납니다. 3타의 내려베기는 수평 진행과 타격 시점을 함께 맞추거나, 별도 전투 데이터 변경과 회귀 검사를 거쳐야 합니다.

`AttackData.reach`는 캐릭터 원점 기준의 넉넉한 게임 판정 범위이며 물리적인 검 길이가 아닙니다. 검을 2.7m로 늘려 간극을 숨기지 않습니다. 실제 접촉 인상과 거리 문제는 모델·트레일·판정의 조합을 플레이 영상으로 확인하고 필요하면 별도 데이터 수정으로 조정합니다.

피격 VFX와 소리는 실제 `landed_hit` 결과에 반응합니다. 클립의 접촉 프레임마다 무조건 피격 효과를 내지 않습니다. .035초 hit pause와 패링/경직/사망/복귀 취소에 클립 시간을 동기화하고 취소된 클립의 지연 이벤트를 폐기합니다.

## G3 · Godot 표현 계층 통합

`ActorVisual.mount_rig(scene, aliases, required_states, facing_correction)`로 검수한 PackedScene을 선택적으로 장착하고 `clear_rig()`로 기존 피벗 표현으로 돌아갈 수 있습니다. 기본 계약은 위 9개 상태와 RESET입니다. 가져온 클립 이름이 다르면 `aliases`에서 상태 이름을 실제 라이브러리/클립 이름으로 매핑합니다.

플레이어와 적의 `presentation_snapshot()`은 공격 ID·실제 elapsed/duration·경직·회피·패링 시간을 값으로 전달합니다. `SkeletalVisualBridge`의 AnimationTree/TimeSeek는 이 시간을 따라 실제 bone pose를 샘플링하며 AnimationPlayer의 자동 재생은 끕니다. 표현 계층이 전투 객체를 수정하거나 클립 이벤트로 피해·이동을 결정하지 않습니다.

장착 전에 실제 Skin과 정규화된 vertex weights·bone binding, RESET·클립·루프 조건·트랙 대상을 검사합니다. 리그 밖/절대 경로·게임플레이 객체·임의 property나 실행 트랙은 거부합니다. 구조 검사와 합성 bone pose의 시간 동기화는 회귀 검사로 확인했으며 최종 자산의 BoneMap·발 접지·크로스페이드·시각 품질은 여전히 별도 검수 대상입니다.

9개 클립은 첫 검수 범위입니다. 강공격/차지·스킬 3종·사망·회복·락온 측면/후방 이동은 이미 게임에 있는 상태이며 이 아트 범위에서는 후속입니다. 전체 게임의 캐릭터를 바꾸기 전에는 각 상태의 별도 모션 또는 검증한 임시 표현 매핑을 명시합니다. 공격·사망 중에 조용히 idle로 돌아가는 것을 합격 처리하지 않습니다. 선택적 스켈레톤 어댑터를 사용하면 미반입 상태의 기존 피벗 표현을 유지합니다.

## G4 · 실제 화면 샷과 플레이 검수

| 샷 | 확인할 내용 |
|---|---|
| 중립 전신 정면·측면·후면 | 같은 비례·의상·스킨과 실루엣, 발바닥·방향·높이 |
| 얼굴과 양손 근접 | 눈·손가락·법선·피부/금속 재질 구분, 그립·무기 관통 |
| 플레이 카메라 idle / 이동 | 현행 FOV 56도와 약 6.7m 뒤쪽 오프셋에서 가독성, 바닥 접촉·머리/천 흔들림 |
| 3연격 1배속·느린 재생 | 준비/판정/회복의 포즈, 실제 적중과 트레일, 벽 근처 발/무기와 취소 |
| 회피·패링 성공/실패·피격 | 실제 코드 창과 연출의 일치, 의상/후광/관절 간섭, 지연 이벤트 누수 |
| 방 입구 → 적 → 출구 | 중앙 교전 공간, 공격 예고, 문·충돌·진행 조건과 카메라 가림 |

첫 방은 기존 world centre (0, 0, -38), 40×40m 바닥을 유지합니다. 중앙 x/z ±11m는 조형물 없는 교전 공간으로 두며, 최종 플레이 동선에서 최소 18m 안팎의 연속된 교전 폭을 다시 확인합니다. 기둥·잔해는 주변부에 배치하고 생성물 때문에 문·적 생성점·플레이 바닥 높이를 이동시키지 않습니다.

Windows Forward+와 웹 Compatibility를 각각 같은 구도로 캡처합니다. 웹은 같은 원본에서 LOD·2K 이하 텍스처·공유 재질·지원하는 조명 대체를 사용하되 얼굴/손/실루엣을 보존합니다. 예산 수치를 만족하는 것만으로 화면이 완성됐다고 판단하지 않습니다.

## G5 · 성능과 확장 조건

- 목표 기기에서 Windows 1080p와 웹 720p를 각각 측정합니다. 목표는 60fps/프레임 예산 약 16.7ms이며 현재 달성 결과가 아닙니다.
- 대표 교전에서 실제 프레임 시간·드로콜·메모리·최초 로딩/셰이더 준비를 기록합니다. 소프트웨어 WebGL의 fps를 목표 GPU 결과로 사용하지 않습니다.
- 정지 화면뿐 아니라 이동·공격·회피에서 실루엣·관절·트레일·피격 가독성을 통과해야 합니다.
- 이 구간의 모델·변형·모션·재질·화면·성능 검수 결과가 남은 뒤에 적 변형·보스·다른 환경으로 확장합니다. 생성 수나 삼각형 수를 품질 완료율로 사용하지 않습니다.
