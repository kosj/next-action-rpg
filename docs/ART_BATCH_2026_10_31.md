# 2026-10-31 애셋 생성 배치

필요한 애셋을 포인트로 생성하도록 사용자가 범위를 확대했습니다. 이번 배치에서는 기존 리라의 경량화·모션 후보를 확장하고, 독립 룬검·성역 기둥·출구 문과 수호병 후보 2종을 생성했습니다. 기존 리라 본체의 유료 재생성은 하지 않았습니다.

**게임에는 hero 검 1개와 첫 courtyard의 기둥 8개·출구 문틀 1개를 프리뷰로 반입했습니다.** 플레이어와 적의 본체는 기존 피벗 모델을 유지합니다. 수호병 후보와 리라의 새 리그·모션을 기본 아바타로 채택한 상태는 아닙니다. 공개 웹 게시와 플랫폼 검증은 해당 배포 실행에서 따로 확인합니다.

[배치 manifest](../art_source/production/batches/2026-10-31/manifest.json)는 실제 실행 ID·사용 포인트·입력과 출력 해시·보관 경로의 원본입니다. 생성 이미지, 원본 3D, Blender 파생 모델, 실제 게임 화면과 최종 품질 승인을 구분합니다.

| 출구 문틀 | [pilgrim_gateway.glb](../game/assets/models/production/pilgrim_gateway.glb) | 7,714 / 2 | 첫 courtyard 북쪽 출구 1개 |

복사한 GLB 3개의 합은 **34,536,204바이트**이며 파생 원본의 크기와 SHA를 보존했습니다. 인스턴스 배치의 삼각형 합은 60,690개입니다. surface 수는 실제 렌더러의 드로콜·그림자 패스·프레임 시간과 별개이며, 파일 크기도 GPU 텍스처 메모리나 최종 PCK/ZIP 증가량을 대신하지 않습니다.

룬검의 canonical 기준은 그립 원점, 날끝 +Y 약 1.19m, 전체 길이 1.35m입니다. 기존 피벗 검은 -Y로 향하므로 새 검에 Z축 PI 보정만 적용했습니다. 기존 손 소켓의 위치와 X 회전, 본체의 전방 보정은 유지하고 `Hilt`·`Guard`·`Blade`·`Blade light` 메시만 숨겼습니다. 수입한 PBR 재질은 프로토타입 단색 재질로 덮어쓰지 않습니다. 새 검은 기존 model 하위에 있으므로 선택적 리그 표시와 미지원 상태 fallback에 함께 따라갑니다.

기둥의 Godot Y-up 크기는 1.6×7×1.6m, 문틀은 17×7.8×1.6m이며 바닥은 0입니다. 기둥 8개와 문 기단 2개의 기존 충돌을 보존했습니다. 기둥의 실제 shaft 반경을 기준으로 단순 실린더와 collar 박스를, 문틀에는 별도의 posts·lintel 단순 충돌을 추가했습니다. 실제 플레이어 캡슐이 통과하는 중앙 12×6m 공간은 비워 둡니다. 자동 trimesh 충돌은 추가하지 않았습니다.

문틀은 항상 보이는 독립 시각물입니다. 기존 `gates[0]`의 잠금 장벽 2개, CollisionShape 자식 순서와 열림·닫힘 제어는 유지합니다. 첫 방 중심 `(0,0,-38)`, 40×40m 바닥, 중앙 local XZ ±11m의 교전 공간과 기존 적 생성점도 바꾸지 않습니다. 다른 구역은 기존 기둥·문 장식을 유지하며 높이용 RNG 호출 순서를 보존했습니다.

[실제 반입 회귀 검사](../game/tests/art_integration_regressions.gd)는 수입 메시의 bounds와 개수, 기존 기단 충돌 보존, 카메라 높이의 기둥·문틀 레이, 실제 플레이어 캡슐의 잠금→해제 통과, 검의 Grip/Tip과 PBR·리그 fallback·quality 0/1을 검사합니다. 실제 웹·Windows 화면과 목표 하드웨어 성능은 이 검사의 별도 확인 항목입니다.

## 리라 32k 정적 메시와 새 리그

무료 Remesh 결과는 실제로 **80,000 → 32,000 삼각형**이며 삼각형 수가 60% 줄었습니다. [정적 원본](../art_source/production/candidates/lyra-web-001/source.glb)은 **14,110,392바이트**로 이전 15,904,156바이트보다 약 **11.3%** 작습니다. 삼각형 감소율을 다운로드 용량 감소율로 표시하지 않습니다.

- 원본은 mesh 1개·재질 1개, 스킨 0개·클립 0개입니다. 별도로 새 리깅을 실행해 스킨 후보를 확보했습니다.
- 텍스처 3개는 각각 2048×2048입니다. 재질 슬롯 연결은 같지만 다시 베이크되어 원본의 인코딩 바이트와 디코딩 픽셀은 동일하지 않습니다.
- 정적 원본의 Blender Z-up REST 높이는 약 1.000576m, 바닥 Z는 약 -0.499917m입니다. 목표 1.82m·발바닥 0 정규화와 실제 스킨·변형 검수가 필요합니다.
- 실제 REST 3면 렌더·구조 검사와 원본 해시 보존을 확인했습니다. 어깨·얇은 갑옷·손가락·얼굴과 천 간섭의 최종 승인은 별도입니다.

### 새 32k 기반 12클립 파생 라이브러리

새 32k 리그의 stock 모션 11개와 `RESET`을 결합한 파생 GLB를 준비했습니다. **32,000삼각형·53본·스킨 1개·12클립**, **18,279,128바이트**이며 [웹 리라 후보 기록](../art_source/production/candidates/lyra-web-001/manifest.json)에서 실제 파생 파일과 해시를 관리합니다. 재반입 REST 높이는 약 **1.820000052m**, 바닥은 약 **-3.58e-7m**이고, 시작·중간·끝 표본에서의 source→target 포즈 오차는 최대 **8.15e-7m**입니다. 원본 12개 SHA는 변하지 않았습니다.

초기 결합은 `idle`의 `LeftUpLeg` rest matrix 오차 **1.29938e-5**가 허용값 **1e-5**를 넘어 중단됐습니다. 이는 남겨 둔 실패 진단이며 현재 결합 상태와 구분합니다. Blender의 `data.transform`이 본 basis를 재구성할 때 발생한 반올림 오차를 피하도록, 연결을 잠시 분리한 본의 head/tail을 한 번 평행이동하고 roll을 유지한 뒤 연결을 복원하는 경로를 적용했습니다. 수정 후에도 **엄격한 1e-5 검사는 그대로 유지**하고 관계·포즈 검사를 다시 통과시켰습니다. 허용오차를 높여 통과시킨 결과가 아닙니다.

새 리그의 provider 원본 중 `idle`·`double_slash`·`left_sidestep`·`right_sidestep` 4개에는 중복 timestamp 문제가 있습니다. 원본을 수정하지 않고 Blender의 해석을 재샘플링한 별도 파생 파일을 검증했습니다. 원본 provider 파일 자체가 수정·합격했다고 표시하지 않습니다.

Blender 후처리에 이어 Godot 4.7.2의 독립 fresh 반입·runtime 감사도 통과했습니다. 53본·53 skin binds·12클립과 비RESET 11클립의 bone pose 변화를 확인했습니다. Godot REST 높이 1.819985688m·바닥 Y 1.40071e-5m는 1e-4m 허용 범위 안이며, 모든 clip의 loop mode는 NONE입니다. 후보 폴더의 `godot-audit-motion-library.json`에 근거를 보관합니다. 기본 gameplay 9상태 매핑·전투 타이밍·발 접지·루프·시각 품질 승인은 남아 있습니다.

## 기존 80k 기반 모션 라이브러리

기존 53본 리그와 locomotion 3개에 stock 모션 8개를 더하고 `RESET`을 포함한 **12클립**의 [파생 라이브러리](../art_source/production/candidates/lyra-motion-library-001/source.glb)를 준비했습니다. 파일은 **20,814,120바이트**이며 위의 새 32k 기반 파생 라이브러리와 별도로 보존합니다.

| 새 후보 클립 | 현재 라이브러리 길이 | 저작·매핑 전 확인 |
|---|---:|---|
| `candidate_sword_slash` | 5.00초 | 유효 베기 구간·방향·그립·접촉 시점 선택 |
| `candidate_double_slash` | 3.70초 | 복수 베기를 현행 약공격 1타로 자동 매핑하지 않음 |
| `candidate_combo_slash` | 4.70초 | 다단 동작과 현행 각 공격의 실제 판정 창 비교 |
| `candidate_cross_block` | 5.00초 | 패링 창 0.22초와 준비·성공 반응 구간 구분 |
| `candidate_left_sidestep` | 약 5.93초 | 회피 방향·접지·게임 이동과의 관계 |
| `candidate_right_sidestep` | 약 5.93초 | 같은 검수; 반대 방향을 이름만으로 선택하지 않음 |
| `candidate_light_hit_back` | 약 1.63초 | 실제 경직 0.15초와 후속 복구 구간 분리 |
| `candidate_hit_fall` | 약 1.73초 | 넘어짐·복구와 피격/사망 상태의 용도 구분 |

세 provider 원본 `double_slash`·`left_sidestep`·`right_sidestep`에는 각각 21개 sampler의 끝 timestamp 중복이 있었고 중복 시점의 값도 미세하게 달랐습니다. 같은 값이라고 간주해 키를 삭제하지 않았습니다. 원본을 보존하고 **Blender가 해석한 동작을 기준으로 0초에서 시작하도록 재샘플링한 별도 파생 GLB**를 만들었습니다. 파생 파일은 12클립 구조 요구를 통과했고 원본 12개 SHA는 변하지 않았습니다. provider 원본 자체의 timestamp 문제나 원본 해석 충실도까지 합격으로 표시하지 않습니다.

이 라이브러리는 기본 gameplay 9상태의 완성 매핑이 아닙니다. 긴 stock 클립 전체를 0.52초·0.70초 공격으로 강제 배속하거나 이름만 바꾸어 적용하지 않습니다. 유효 구간을 선택하고 실제 베기 방향과 시작·판정·회복 창, 취소·hit pause·패링·회피·피격, 의상·발 접지·루프를 검수해야 합니다.

## 후속 채택 기준

원본·참조·설정·완료 task·사용 포인트·선택한 공개 범위와 SHA를 보관합니다. 이미 완료한 task를 입력으로 고정해 유료 upstream을 다시 실행하지 않으며, 임시 서명 URL·계정 원문·OAuth 정보는 공개 저장소에 넣지 않습니다.

정적 프리뷰의 반입과 캐릭터 후보의 생성 성공은 최종 아바타·AAA 아트 완성이나 목표 60fps의 합격이 아닙니다. 수호병은 실제 3면·형상 검수에서 native 후보를 주 후보로 선택했습니다. 남은 핵심은 수호병 리깅·모션, 리라의 기본 전투 6모션 저작·전체 상태 표현, 발 접지·무기 그립·재질·실제 플랫폼 화면과 성능입니다. 수치와 전체 반입 계약은 [대표 구간 검수 계약](ART_SLICE.md)을 따릅니다.
