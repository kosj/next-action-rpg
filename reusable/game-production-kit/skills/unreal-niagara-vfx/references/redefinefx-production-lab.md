## 2. 개선 요청의 실행 순서

1. **증상 하나를 선정한다.** “검기가 흰 띠다”, “접촉 전 이미 부서진다”, “연기가 전투를 가린다”처럼 실제로 보이는 문제를 쓴다. 모션·카메라·타격 판정의 문제라면 VFX 문제와 분리한다.
2. **기준을 고정한다.** source/asset hash·카메라·노출·render scale·시드·gameplay 입력/이벤트 정책을 기록한다. 동적 AI 궤적은 실제 차이를 기록하고 똑같았다고 가정하지 않는다.
3. **관찰→가설→수정을 연결한다.** 참고 글의 사실, 우리 효과의 원인 가설, 바꿀 제어군, 기대 결과와 기각 조건을 실험 기록 한 줄에 적는다. 아직 관찰하지 않은 원인은 가설이다.
4. **주 형태를 먼저 만든다.** core/body·진행 방향·두께/끝 감쇠만 고친 후보를 본다. 파티클·왜곡·광원을 전부 동시에 바꾸지 않는다.
5. **한 제어군씩 비교한다.** 형상 → 흐름/감쇠 → 반응 레이어 → 작은 변형 → 최적화 순서를 기본으로 하되 원인에 맞춰 조정한다. 비교 중 바뀐 조건을 모두 남긴다.
6. **인과관계를 시험한다.** 실제 접촉·빗나감·벽·인접 비대상·연속 발동/중단에서 상태와 표현이 맞아야 한다. 큰 폭발이 난 것과 올바른 대상에게만 반응한 것은 다른 결과다.
7. **정상1배속에서 판정한다.** 실제 게임 카메라로 준비→release→contact/whiff→tail을 연속 검토한다. 유한 프레임·수치·기능 검사로 원인을 찾고 그것만으로 질감을 승인하지 않는다.
8. **채택과 비용을 묶어 기록한다.** 읽히는 개선, 회귀, CPU/GPU/메모리/전송 변화와 남은 항목을 적는다. 기각안을 보존하고 최종 후보만 전체 교전/대상 빌드로 확대한다.

## 3. 증상별 수정과 기각 조건

다음 표는 강좌에서 그대로 가져온 값이 아니라 우리 효과를 진단하기 위한 실험 설계다.

| 증상 | 우선 바꿀 것 | 반드시 고정/확인할 것 | 기각할 결과 |
| --- | --- | --- | --- |
| 흰 띠·납작한 검기 | mesh 단면/곡률·끝 taper, core/body 밝기 분포 | 실제 release/진행 경로·피해 범위, 사선/근거리 | noise만 늘고 실루엣이 그대로이거나 몸체를 가림 |
| 힘 없이 흐르는 꼬리 | 방향 흐름·속도 대비·잔향 감쇠 | 원래 입력/공격창·소유 시계 | 연출 때문에 입력 지연, tail이 다음 공격 예고를 덮음 |
| 접촉 전 손상/섬광 | 원상태→접촉 반응의 event/state 분리 | 확정 hit identity와 실제 충돌점 | whiff에도 손상/명중 burst 발생 |
| 주변이 한꺼번에 반응 | 대상/범위/중복 trigger 제한 | 의도된 범위 공격과 인접 비대상 | 원래 단일 접촉이 전체 파괴·피해로 확장 |
| 복사된 듯 반복되는 파편 | 크기/회전/수명/variant의 작은 변형군 | 진단 시 고정 시드, gameplay RNG와 collider | 시드가 판정을 바꾸거나 눈에 띄는 패턴만 추가 |
| 보호막이 효과 없이 통과시킴 | 의도된 충돌·반발·끌림 중 하나를 명시 | 안/경계/밖 표본의 위치·속도 반응 | 경계 그림만 있고 요구한 힘은 없거나 장식이 피해를 변경 |
| 작은 입자가 주 효과를 가림 | 큰 조각/주 형태와 미세 입자의 역할·한도 | 전체 해상도와 배포 압축본 양쪽 | full preview에서만 보이는 미세 입자에 비용을 과소비 |
| smoke가 불투명 상자로 보임 | source 범위·domain/bounds·밀도 곡선/alpha | emitter 좌표와 전체 수명 | 해상도/밝기만 늘려 경계·가독성 결함을 숨김 |

## 4. 저작·시뮬레이션·표시 제어를 나눠 튜닝한다

**Unreal:** 실제 template의 Source/Simulation/Render를 분리한다. [Epic Fluids Reference](https://dev.epicgames.com/documentation/en-us/unreal-engine/niagara-fluids-reference-in-unreal-engine)를 대조해 먼저 주입 위치/속도와 domain을 맞추고, 흐름·감쇠를 조정한 뒤 density/temperature의 표시 mapping을 다듬는다. 시뮬레이션 밀도, opacity·색, 외부 힘은 같은 제어가 아니다. grid 해상도와 render sampling 비용도 별도로 측정한다. 특정 template의 이름·수치를 다른 시스템에 강제하지 않는다.

**Godot/Blender:** 같은 의도를 Blender의 저작/베이크와 runtime mesh·mask·alpha·local/world 입자 선택으로 재작성한다. Niagara 속성을 Godot에 같은 이름의 API로 만들지 않는다. 시뮬레이션을 굽는 경우 cache→이미지→atlas→실제 import를 각각 확인하고, 카메라/부피 상호작용의 손실을 명시한다. 웹에서 큰 형태를 mesh로 유지하고 필요한 연기만 작은 atlas로 시험하는 것은 프로젝트별 후보이지 항상 최적이라는 결론은 아니다.

**파괴가 실제 요청 범위일 때:** Unreal의 anchor/strain/force는 [Epic Chaos Fields](https://dev.epicgames.com/documentation/en-us/unreal-engine/chaos-fields-user-guide-in-unreal-engine)와 설치본에서 확인한다. 손상 전 시각 상태와 실제 물리 활성화·게임 피해를 구분한다. 영화 장면의 선행 활성화 기법을 액션 RPG의 선행 명중으로 옮기지 않는다. Godot에서도 시각용 조각과 gameplay 물리의 권한을 별도로 설계한다.

## 5. AI/MCP로 편집할 때의 실행 계약

실제 연결된 도구/schema·대상 project/asset를 읽는다 → 변경 전 snapshot을 고정한다 → 작은 변경을 적용한다 → 저장한 asset/매개변수를 다시 읽는다 → 컴파일/참조를 검사한다 → 정상 입력으로 플레이한다 → 전후 화면/비용을 검수한다.

읽기에서 확인하지 않은 API·plugin·이벤트명을 생성하지 않는다. 변경 호출의 반환 성공·로그와 실제 graph·표시 성공을 구분한다. 무관한 에셋/기본값·피해/타이밍을 묶어 바꾸지 않고 실패한 변경을 복원할 수 있게 남긴다. 이 절차는 공개 소개에서 착안한 자체 작업 원칙이며 특정 유료 강의의 MCP 구현을 확인했다는 뜻이 아니다.
