# 실시간 전투 VFX 제작

사용자의 효과 요청을 **제작 가능한 설계 → 자산 → 런타임 연결 → 실제 화면 검수**로 완성한다. 이 폴더 전체를 다른 프로젝트의 스킬 경로에 복사할 수 있다. [제작 양식](references/vfx-brief.json), [효과별 recipe](references/effect-recipes.md), [검수 기록](references/review-checklist.md)을 함께 사용한다.

공개 RedefineFX 강좌 소개에서 확인한 효과 분류를 출발점으로 삼아, 공식 엔진 문서와 실제 게임 제작 원칙을 조합한 **독립 작성 절차**다. [출처와 열람 범위](references/source-notes.md)를 먼저 확인한다. 강의 전체 시청·실습 이수나 원본 프로젝트 복제본이 아니다. 새 프로젝트의 적용·시각·성능 검증은 `pending`에서 시작한다.

## 1. 작업을 구체화한다

1. 요청과 기존 지침에서 엔진/Blender 버전, 렌더러, 웹·모바일·Windows 대상, 카메라 거리, 효과의 역할과 현재 문제를 확인한다. 이미 주어진 값은 다시 묻지 않는다. 미지정 값은 작은 후보 실험으로 정하고 가정으로 기록한다.
2. 참조에서 원하는 **실루엣, 진행 방향, 시간 대비, 재질 반응**을 설명한다. 예를 들어 “더 강하게”는 긴 준비 뒤 짧은 방출, 진행체의 두께/끝 감쇠, 접촉점의 국소 반응처럼 바꿔 적는다. 밝기·입자 수 증가만을 목표로 삼지 않는다.
3. 효과가 예고, 공격 궤적, 실제 진행체, 확정 접촉, 잔향 중 무엇을 표현하는지 정한다. 피해·방어·충돌의 권한과 별도인지, 실제 collider와 어디까지 일치해야 하는지 기록한다.
4. 기존 source·셰이더·텍스처·동영상과 SHA를 고정한다. 후보 경로에서 작업하고 원본과 기각안을 보존한다. 자료 열람 권한과 제공 자산의 사용·재배포 조건은 구분한다. 이미 위임받은 작업에 새 승인 단계를 만들지 않는다.

## 2. 레이어와 시간을 먼저 설계한다

한 효과를 아래 역할로 분해한 뒤 필요한 것만 선택한다. 이것은 자체 제작 틀이며 강좌의 실제 노드 구성으로 인용하지 않는다.

| 역할 | 제작할 것 | 확인할 점 |
| --- | --- | --- |
| 준비/예고 | 응축되는 작은 빛, 방향 흐름, 제한된 먼지 | 상대가 공격 방향과 시작을 읽을 수 있는가 |
| 주 형태 | 검기 메시, 불기둥, 보호막 또는 탄체 | 정상 카메라에서 크기·방향·두께가 읽히는가 |
| 빠른 디테일 | 국소 불꽃·전기·작은 파편 | 주 형태와 몸체를 가리지 않는가 |
| 접촉 | 실제 충돌점/법선을 따르는 섬광·재질 반응 | 빗나감과 구분되고 접촉 순간에 시작하는가 |
| 잔향 | 감속하는 연기·먼지, 흐트러지는 끝 | 주 타격보다 약하며 다음 공격 전에 정리되는가 |

시간표는 gameplay의 시작·release·contact·끝을 기준으로 만든다. 충격의 강도는 준비/방출/잔향의 **대비**로 조절하고, 입력 지연이나 기존 active 창을 VFX 때문에 몰래 늘리지 않는다. 무기 궤적·진행체와 접촉 burst의 시계를 분리한다. 카메라·음향을 쓸 때는 동일한 확정 이벤트에 연결하고 기존 사용자 강도/비활성화 설정을 따른다.

## 3. 표현과 렌더 경로를 고른다

- **메시+공간 셰이더**: 방향과 두께가 중요한 검기·링·보호막의 주 형태. 이동 거리와 시야각이 바뀌어도 판처럼 보이지 않는지 먼저 검사한다.
- **파티클**: 불꽃·먼지·작은 파편·연기의 분산. GPU/CPU 선택은 실제 기능·기기 비용으로 정한다. Godot Compatibility에서 GPU 파티클 전체가 불가능하다고 단정하지 않는다. 수동 방출 API, 내장 trail, SDF collision의 지원은 별도로 확인한다.
- **플립북**: 비싼 연기/불 시뮬레이션의 시각을 베이크한 이미지 시퀀스. 런타임의 부피·상호작용을 그대로 보존하는 방식은 아니다. 카메라/광원 변화에 대한 한계를 적는다.
- **고급 분기**: 지원되는 렌더러의 볼륨·굴절·추가 조명. 웹 기본 효과의 인지와 게임 규칙은 낮은 분기에서도 유지하고, 상위 분기를 기본 성공의 전제로 삼지 않는다.

첫 실험은 작은 기술 씬에서 **실제 목표 렌더러로 보이는지** 확인한다. 컴파일 성공 뒤 검게 나오거나 화면이 하얗게 포화되면 전체 게임 촬영 전에 수정한다. 렌더러별 근거는 [출처 노트](references/source-notes.md)의 버전에서 다시 확인한다.

## 4. Blender에서 베이크 자산을 만든다

1. 복제한 `.blend`에 단위·축·원점·domain/emitter·프레임 구간·FPS·시드·캐시 경로를 기록한다. 캐시는 후보별로 분리한다. 필요한 시뮬레이션과 렌더가 정상 종료됐는지 각각 확인한다.
2. 저해상도 시뮬레이션으로 실루엣·팽창/감속·잔향부터 검토한다. 승인할 형태가 잡힌 후 detail을 올린다. 큰 박스 같은 domain 경계, 바닥 관통, 반복되는 소용돌이를 먼저 고친다.
3. 고정 카메라·노출·프레임 범위로 투명 배경 시퀀스를 렌더한다. 주 형태가 프레임에 잘리지 않게 여백과 pivot을 고정한다. 색, 마스크, 필요하다면 법선/다른 패스의 의미·색공간을 명시한다.
4. 실제 프레임 수와 grid를 정해 atlas로 묶는다. 예: 정수 셀 크기를 사용하고 `frames <= columns * rows`를 지킨다. 시작 프레임·행 방향·재생 FPS·마지막 프레임 유지/종료·루프를 기록한다. 빈 셀을 재생하지 않는다.
5. straight/premultiplied alpha를 기록하고 해당 혼합 방식에 맞춰 가져온다. 검은/밝은 배경에서 외곽 halo를 확인한다. 무조건 RGB를 alpha로 나누지 말고 원본의 표현을 먼저 판별한다. 나누는 변환이 필요하면 alpha 0의 NaN을 막는다.
6. 셀 외곽 여백·mipmap 번짐·압축 후 banding·프레임 경계 점프를 실제 반입 텍스처로 검사한다. PNG 크기를 GPU 메모리로 간주하지 않는다. RGBA8의 `폭×높이×4`는 압축 전 base-level 추정치이며 mip/압축/드라이버의 실제 비용은 별도 측정한다.

Niagara를 실제 사용 가능한 프로젝트라면 공식 Baker가 대안이다. Niagara cache나 Unreal 전용 자산을 Godot가 직접 실행한다고 설명하지 않는다. Blender/플립북은 **의도와 결과를 재저작하는 경로**다.

## 5. Godot에 연결한다

1. `VFXRoot` 아래 역할별 메시/파티클을 나누고 주 형태부터 연결한다. 실제 렌더링 재질과 파티클 process 재질은 구분한다. 각 레이어의 수명·좌표계·AABB·그림자·깊이·혼합 방식을 명시한다.
2. emitter가 따라가는 local 좌표와 방출 후 남는 world 좌표를 구분한다. 최종 무기 marker를 따라가는 trail은 포즈 평가 후 같은 프레임에 표본화한다. 시작/중단/순간이동/복귀 때 과거 이력을 연결하지 않는다.
3. gameplay 이벤트와 immutable한 식별자/접촉 정보를 받아 표현한다. 미리 계산한 예고 이펙트로 실제 명중을 만들어 내지 않는다. 진행체는 권한 있는 원점·방향·거리·차단 위치를 따른다. 근접과 검기 등 전달 수단별 표현을 구분하면서 원래 공격 ledger를 보존한다.
4. 효과별 시간 정책을 정한다. 공격 동결을 따르는 trail, 이미 발사된 진행체, 장면 pause의 동작은 다를 수 있다. shader `TIME`은 장면 pause와 동일한 시계가 아니므로 필요한 효과는 명시적 `effect_age`/progress로 구동한다. 공유 재질의 mutable uniform으로 다른 인스턴스의 시간을 덮어쓰지 않는다.
5. 종료·취소·소유자 해제·장면 전환·복귀의 정리를 구현한다. 풀링이면 모든 시간/시드/좌표/재질 상태를 초기화하고, 최대 동시 효과와 emitter/입자/조명 수를 제한한다. 값은 프로젝트 예산으로 정한다.
6. unshaded 효과의 실제 출력 색과 alpha를 확인한다. 발광 설정만으로 모든 렌더러에서 빛나거나 bloom이 생긴다고 가정하지 않는다. depth test를 끄거나 화면 전체 additive로 가려서 벽 관통·평면 실루엣을 숨기지 않는다.

## 6. 실제 전투에서 채택 여부를 판단한다

같은 빌드·품질·카메라의 수정 전후를 비교한다. **정상 1배속 연속 화면**에서 준비→방출→접촉/빗나감→회수까지 보고, 원인 진단에 정지 프레임과 수치 검사를 사용한다. 실제로 듣지 않았다면 음향 검수는 남겨 둔다.

- 정면/사선/측면, 가까움/멀어짐에서 주 형태와 끝 감쇠가 읽혀야 한다. 검기가 흰 띠·불투명 상자·납작한 부채처럼 보이면 밝기를 올리기 전에 형상·밀도·시점을 고친다.
- 명중/빗나감/방패/벽/다중 적·연속 발동·회피 중단·pause/restore에서 적과 캐릭터의 동작, 공격 예고, HUD가 읽혀야 한다.
- 실제 웹 export를 PC와 모바일 크기에서 확인한다. render scale/품질/밝은 바닥/어두운 배경에서도 비교한다. 투명 quad가 화면을 덮는 면적과 중첩을 입자 수와 함께 살핀다.
- 같은 조건에서 효과 OFF/ON의 CPU/GPU frame time, draw call, 메모리·전송 용량·첫 사용 hitch를 측정한다. 도구가 제공하지 않는 GPU 지표는 `pending`으로 남긴다. 녹화 FPS나 소프트웨어 렌더러를 목표 기기 성능으로 쓰지 않는다.

## 전달물과 완료 조건

제작 요청은 설계 문서만으로 끝내지 않는다. 해당 요청 범위의 **원본/베이크 recipe·텍스처/메시·셰이더/씬·연결 코드·짧은 비교 영상·검수 기록**을 전달한다. 이번 요청이 스킬 작성 자체라면 스킬·템플릿·출처·독립 패키지 검증까지 완료하고 실제 게임 변경을 수행했다고 표시하지 않는다.

결과에는 채택/기각 이유, 버전과 source hash, 관측한 범위와 미검증 항목을 적는다. 기능 통과·실제 가시성·연속 시각/음향·목표 하드웨어·최종 AAA 품질을 각각 판정한다. 다음 작업은 가장 크게 보이는 결함 하나를 고치는 작은 제작 단위로 정한다.
